## 二、场景与结果

### 场景 A:语义缓存——未命中 vs 命中(核心亮点)

- 方法:同一问题"缓存穿透是什么,如何解决"连问 3 次;延迟与 token 从 MySQL `t_qa_record`(elapsed_ms/total_tokens/cache_hit 落库)精确统计

| 请求 | 命中缓存 | 端到端延迟 | token 消耗 |
|---|---|---|---|
| 第 1 次(冷启动) | 否 | **2290 ms** | 1055 |
| 第 2 次(同问) | 是 | **588 ms** | **0** |
| 第 3 次(同义改写"什么是缓存穿透,有哪些解决办法") | 是 | **447 ms** | **0** |

- **延迟降低 74% ~ 80%;token 消耗降为 0**
- 同义改写命中证明语义匹配(问题 embedding 余弦相似度 ≥ 0.92)生效,不是简单字符串去重

### 场景 B:令牌桶限流 burst

- 方法:JMeter 100 线程并发 burst 打"已缓存"问题(命中路径不调大模型,零 token 风险);响应断言检查 `cacheHit` 事件
- 结果:

| 指标 | 数值 |
|---|---|
| 总请求 | 100(6 秒内) |
| 通过 | **35 个,全部缓存命中**(数据库确证,通过速率 ≈ 5.8/s) |
| 拒绝 | **65 个**(5s 内拿不到令牌,返回 error 事件,不落库、不消耗 API) |

- 通过速率与配置的 `rag.rate-limit.qps=5` 吻合(略高为令牌桶初始容量)
- 被拒请求发生在限流层(先于 embedding/检索/LLM 一切昂贵操作),数据库与 API 零成本

### 场景 C:文档入库链路

- 方法:上传 2 个文档,轮询 `GET /api/documents/{id}` 到 SUCCESS;ES 分块数前后对比

| 文档 | 大小 | 端到端耗时 | 分块 |
|---|---|---|---|
| TECH-STACK.md | 3.9 KB | **2.2 s**(PENDING→PARSING→SUCCESS 流转可见) | 8 |
| RAG项目规划.md | 8.5 KB | **1.0 s** | 14 |

- ES kb_chunks:35 → **57**(+22,与分块总数一致,无丢失)
- 链路:上传落库(PENDING)→ MQ 投递 → Tika 解析 → 400 字分块 → bge-m3 批量向量化 → ES 索引 → SUCCESS

## 五、面试注意与已知事实

- **限流是 Guava 单机令牌桶**(`RateLimiter.tryAcquire(5s)`),不是 Redis 分布式——集群部署时每个实例各自 5 QPS,被追问"多实例怎么办"要能答(思路:共享 Redis 计数或网关层限流)。每日 token 预算才是 Redis 实现(INCR + TTL 回收)。
- **限流在语义缓存之前**:缓存命中的请求也要先过令牌桶,这是刻意的成本控制顺序(避免 embedding API 也被打爆)。
- **缓存命中路径仍有一次 embedding 调用**(要对问题向量化才能算相似度),只是省掉了大模型调用;回答"缓存命中是否完全无成本"时注意这个细节。
- **没有独立检索接口**,混合检索延迟未单独压测(场景 A 的 2290ms = embedding + 检索 + LLM 全链路)。
- 压测残留:ES 新增 22 分块(doc id 3/4),t_qa_record 新增 38 条,均为真实数据,无害。
