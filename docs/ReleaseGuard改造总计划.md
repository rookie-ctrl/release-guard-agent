# ReleaseGuard 改造总计划

## 1. 项目目标

把现有单轮 RAG 知识库演进为“微服务发布变更评审 Agent”。系统围绕一次发布评审持续多轮对话，自主查询发布信息、测试报告、代码变更、数据库脚本、服务依赖、监控指标和知识库，并在人工确认后创建审批单。

重点不是展示模型会调用函数，而是实现一个可控、可恢复、可审计的 Java Agent 执行平台。

## 2. 现有能力复用

| 现有能力 | ReleaseGuard 中的角色 |
|---|---|
| 文档异步入库 | 发布规范、故障复盘、回滚手册入库 |
| BM25 + kNN + RRF | `searchKnowledge` 工具 |
| 模型策略模式 | Agent Tool Calling 与文本回答使用同一模型策略 |
| Redis | 热点缓存、会话锁、预算控制 |
| RabbitMQ | Agent Run 异步调度与失败重投 |
| MySQL | 会话、步骤、工具调用、确认和事件持久化 |
| SSE | 计划、工具调用、确认和答案实时推送 |

## 3. 分阶段实施

1. **工程基线**：保护环境变量，引入 Flyway 和 Actuator，固定业务演示数据。
2. **领域模型**：建立 Session、Run、Step、Message、ToolInvocation、Confirmation、Review、Event 数据模型。
3. **工具平台**：统一工具注册、参数校验、超时重试、幂等和风险分级。
4. **Agent Engine**：受控 Tool Calling 循环，限制最大步骤、工具次数和总执行时间。
5. **RAG 工具化**：增加文档分类与服务过滤，把混合检索封装成知识检索工具。
6. **长对话记忆**：最近消息、历史摘要、结构化发布评审状态三层记忆。
7. **异步恢复与 SSE**：RabbitMQ 调度、步骤持久化、事件重放、人工确认后恢复。
8. **稳定性与测试**：幂等、并发控制、超时、故障恢复、指标与压测。

## 4. 范围边界

演示环境使用 Mock DevOps Gateway，不声称真实接入 GitLab、Jenkins 或 Prometheus；所有接口均通过端口适配器设计，后续可替换真实实现。项目不自动发布或回滚，只允许创建发布审批，避免为了展示 Agent 引入不必要的高风险能力。

## 5. 最终演示闭环

1. 用户请求评审 `order-service v2.3.7`。
2. Agent 查询版本、测试、代码、SQL、依赖和指标。
3. Agent 检索历史事故与发布规范。
4. Agent 发现字段删除、覆盖率不足、缺失回滚 SQL，给出高风险结论。
5. 用户补充兼容方案和回滚计划，Agent 在后续对话继续使用已有上下文。
6. Agent 请求创建审批，后端强制人工确认。
7. 用户确认后幂等创建审批单，完整过程可审计、可重放。

## 6. 文档约定

每完成一个阶段，在 `docs/release-guard/` 下记录：问题背景、设计取舍、关键实现、失败保护、验收方式和面试话术。代码与文档同步推进，不在全部完成后补写回忆式文档。
