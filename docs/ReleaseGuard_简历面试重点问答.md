# ReleaseGuard：简历面试重点问答

依据简历中的 ReleaseGuard 项目描述与当前项目源码整理，共 **14 题**。已同步 2026-10-13 的提示词防护改造。答案按面试口述方式组织；“实现边界”用于应对追问，区分已经实现的功能与后续改进。

## 1. ReleaseGuard 解决什么问题？从提交 PR 审查问题到看到结论，完整流程是什么？

**参考回答：**

ReleaseGuard 面向公开 GitHub PR，结合代码变更、必要的源码上下文、CI 状态和知识库规范，辅助判断变更风险，并给出带证据的发现与建议。

用户创建 PR 会话时，后端读取并保存 PR 的提交快照。提交问题后，在同一数据库事务中保存 Run、用户消息和 Outbox 任务。后台把任务发送到 RabbitMQ，消费者取得 Redis 执行锁后启动 Agent。Agent 根据模型返回的工具请求读取 PR 信息、文件、diff、CI 或规范，把工具结果反馈给模型，直到得到最终回答。过程中的步骤、工具调用和事件都会保存；前端订阅该 Run 的 SSE，展示执行过程和最终结论。

`创建 Session → 保存 Run 与 Outbox → RabbitMQ 调度 → Agent 工具循环 → 保存结论 → SSE 展示`

**对应代码：** `AgentSessionService`、`AgentOutboxPublisher`、`AgentRunConsumer`、`AgentRunner`、`AgentEventService`。

## 2. 为什么使用 Agent？LangChain4j 和自己的后端分别负责什么？

**参考回答：**

一次性读取 diff 再调用模型，适合资料固定、范围较小的检查。实际 PR 可能包含很多文件，模型需要根据已发现的问题继续读取上下文、检查 CI 或查找规范，所以我使用“模型决定下一步、工具获取事实、结果反馈给模型”的循环。

LangChain4j 提供模型客户端、消息、工具规格以及 Tool Calling 请求和结果的数据结构。执行循环、工具白名单、参数校验、超时重试、人工确认、持久化和 SSE 都由后端控制。模型可以提出工具调用请求，是否允许执行由后端决定。

**实现边界：** 当前 Agent 循环由 `AgentRunner` 实现；提示词中的计划要求不保证模型一定完成所有检查，因此结论必须说明已检查和未检查的范围。

## 3. Session、Run、Step 为什么分开保存？Run 的状态怎样变化？

**参考回答：**

Session 表示一个持续的评审会话，保存 PR 快照和历史摘要；Run 表示用户一次提问触发的执行，保存状态、结论和工具调用次数；Step 表示执行中的具体记录，例如工具调用、等待确认、最终回答或错误。一个 Session 可以有多个 Run，一个 Run 可以有多个 Step，分开保存便于追问、定位失败和回放执行过程。

正常流程是 `CREATED → RUNNING → COMPLETED`；发生异常或超过执行限制会进入 `FAILED`；高风险工具使 Run 进入 `WAITING_CONFIRMATION`，确认或拒绝后回到 `RUNNING` 继续执行。消息表有自己的自增主键，相同的 sessionId、runId 用于关联，不会因此覆盖旧消息。

**实现边界：** 当前没有独立的 `TIMED_OUT` 状态，超时按失败处理；`CANCELLED`、`WAITING_USER_INPUT` 已定义，但尚未形成完整的取消和等待补充信息流程。Step 数量也不等于模型推理轮数。

## 4. 一次 Tool Calling 怎样完成？ToolDefinition、AgentTool 和 GitHubAgentTool 如何联系？

**参考回答：**

`ToolDefinition` 保存工具名称、描述、参数规格、风险、超时和重试配置；`AgentTool` 定义统一执行接口；`GitHubAgentTool` 是 GitHub 工具的具体实现，负责根据 runId 找到会话的 PR 快照，再执行保存的 action。

启动时，Spring 调用配置类的 `@Bean` 方法创建工具对象。配置类把具体 Lambda 通过构造方法传给 `GitHubAgentTool`；record 的构造方法把它保存为 action。Spring 再将这些 `AgentTool` Bean 注入 `ToolRegistry`，形成“工具名 → 工具对象”的映射。

运行时，模型收到工具规格后返回工具名和 JSON 参数；后端查注册表、校验并执行 `tool.execute(runId, arguments)`，由 `action.apply(snapshot, arguments)` 调用 `GitHubGateway`。结果转成 `ToolExecutionResultMessage` 加入上下文，下一轮模型才能根据结果继续判断。

**实现边界：** 运行时不会回配置类寻找实现。这里主要是统一接口、注册表和回调；模型厂商切换则使用 `ChatModelStrategy` 策略模式，由配置的 provider 选择策略、model 指定具体模型。

## 5. 怎样防止模型调用不存在的工具，或通过参数越权？提示词白名单够不够？

**参考回答：**

提示词只能引导模型，安全限制必须由后端执行。我只注册允许调用的工具，并按 PR/演示模式的明确工具集合过滤工具规格；模型返回请求后，再检查模式、工具名称、风险等级和参数。当前校验覆盖字符串类型和长度、必填字段、额外字段、重复 JSON 键、尾随 JSON、分页、路径与枚举；GitHub 工具还绑定当前 Session 的仓库与提交快照。

PR 描述、代码和检索文档都是待分析资料，里面的指令不能作为执行权限来源。未知工具或非法参数会抛异常，当前 Agent 将本次 Run 标记为失败。

**实现边界：** 当前已校验工具使用的字符串与枚举参数，新参数类型需补充后端校验；没有让模型自动修正非法参数的循环。系统规则与资料分开传入，但自由文本仍可能影响模型分析，不能宣称彻底防住提示词注入。

**对应代码：** `ToolRegistry`、`ToolExecutionService.validateArguments()`、`GitHubAgentTool`、`ConversationMemoryService`、`PromptSecurity`。

## 6. 怎样限制 Agent 不断推理、重复调用工具或长时间不结束？

**参考回答：**

我在 Agent 和工具执行两个层次设置预算：

| 限制 | 当前配置 | 控制位置 |
| --- | --- | --- |
| 主循环模型推理轮数 | 12 轮 | `AgentRunner` 的循环上限 |
| 工具调用次数 | 20 次 | `AgentRunner` 计数并保存到 Run |
| 单次工具尝试等待时间 | 默认 5 秒；GitHub 20 秒 | `ToolExecutionService` 的限时等待 |
| 执行时长检查 | 180 秒 | `AgentRunner` 每轮调用模型前检查 |

普通只读工具默认允许重试一次，因此最多尝试两次；每次分别限时，中间退避 100 毫秒。两次都等到超时时，等待约为 `5 + 0.1 + 5 = 10.1` 秒，另有执行开销。GitHub 工具当前不重试，非只读工具也不自动重试。

**实现边界：** 180 秒是在每轮开始时检查，不能保证阻塞中的模型或工具立即终止。`CompletableFuture.cancel(true)` 也不保证停止底层请求，重试可能与第一次尚未结束的请求重叠。确认后重新进入执行方法会重置轮数和计时起点，工具次数继续累计；历史摘要调用不计入这 12 轮。当前依靠预算终止循环，没有专门的重复计划检测。

## 7. 为什么用 RabbitMQ 和事务 Outbox？直接保存 Run 再发消息有什么问题？

**参考回答：**

Agent 执行时间较长，RabbitMQ 让提交接口快速返回 runId，后台异步处理任务。直接保存 Run 再发消息存在一致性窗口：数据库提交成功但消息发送失败，任务可能一直没有被执行；先发消息再提交数据库，也可能让消费者读取不到 Run。

所以我把 Run 和待发送的 Outbox 记录放在同一事务中，确保一起提交或回滚。后台每秒扫描到期的待发记录，发送失败后指数退避，最大间隔 60 秒；失败达到 10 次标记为 `DEAD`，保留错误信息供排查。

**实现边界：** Outbox 解决的是数据库与待发任务的一致性。当前发布器调用发送方法后就标记 `PUBLISHED`，要完善消息到达保障，还需要结合 Broker 确认、退信处理和 DEAD 任务告警补偿；不能直接宣称消息绝不会丢失。

## 8. MQ 重复投递时，怎样避免重复执行？Redis 锁和工具幂等分别解决什么问题？

**参考回答：**

我使用三层控制。首先，消费者按 runId 获取 Redis 锁，减少同一个 Run 的并发执行；锁值使用随机令牌，释放时用 Lua 比较令牌再删除，避免误删别人的锁。其次，执行入口检查 Run 状态，已经完成或失败的任务不重复执行。最后，工具调用使用 runId、工具名和参数计算幂等键，已有成功记录就复用保存的结果。

对于上次处于 `RUNNING`、结果不确定的工具调用，只读工具允许重新执行；非只读工具要求人工核对，避免直接重复产生副作用。内部重试不增加 Agent 的工具调用计数，但模型再次提出调用仍然计数。

**实现边界：** 当前锁有效期为 120 秒且没有续期，比 180 秒执行预算短，长任务可能在执行中失去互斥保护。另外，外部操作成功但本地结果未保存的窗口仍然存在，因此不能宣称 Exactly Once；完善方案需要锁续期及外部系统幂等支持。

**对应代码：** `AgentRunLock`、`AgentRunner`、`ToolExecutionService`。

## 9. 哪些操作需要人工确认？怎样确保确认的是这一次具体操作？

**参考回答：**

工具执行风险分为 `READ_ONLY`、`LOW_RISK`、`HIGH_RISK` 和 `FORBIDDEN`。高风险工具暂停执行并请求人工确认，禁止级别即使确认也不能执行。工具执行风险由后端定义，与模型评估 PR 得到的 LOW、MEDIUM、HIGH 业务风险是两回事。

确认记录绑定 Session、Run、工具名、原始参数、随机令牌和 10 分钟有效期。用户提交决定时，后端加数据库行锁，校验待处理状态、有效期、令牌以及 Run 是否等待确认；批准后使用记录中保存的工具和参数执行，不能由前端重新指定另一项操作。拒绝则不执行工具，并把拒绝结果反馈给 Agent 继续评审。

**实现边界：** 当前高风险示例是演示模式的 `createReleaseApproval`，底层为 Mock；PR 模式开放的是只读工具和知识检索。Agent API 已校验创建者的浏览器会话归属，但这只是匿名会话隔离，尚未接入账号登录和企业权限体系。

**对应代码：** `AgentRunner.requestConfirmation()`、`AgentConfirmationService`、`ConfirmationRequestRepository`。

## 10. PR 在评审过程中更新了怎么办？怎样保证结论对应同一版本？

**参考回答：**

创建 Session 时保存 head SHA、base SHA 和 merge base SHA，后续 GitHub 工具从会话读取这份快照，源码上下文按固定提交读取。读取 PR 数据时会检查当前 head、base 是否仍与快照一致；关键读取前后也会校验。如果提交或目标分支发生变化，就报错要求创建新的评审会话，避免混用不同版本的证据。

大 PR 采用文件分页、diff 分段和按需读取源码的方式。缺失 patch、截断和未读范围需要明确标记，结论说明检查范围，并引用文件路径、行号、提交 SHA 和规范出处。CI 没有结果或权限不足应保留为未知，不能当作测试通过。

**实现边界：** PR 结论已改为结构化输出，后端核对 evidenceId、当前会话、成功工具调用、已传入上下文的数据、文件、SHA、源码行号和规范片段。本轮 CI 由后端直接展示。引用存在不代表模型判断正确，也不代表已经检查全部文件。

**对应代码：** `GitHubGateway`、`PullRequestSnapshot`、`ConversationMemoryService`、`ReviewConclusionService`。

## 11. 多轮追问时怎样管理记忆，避免上下文越来越长？

**参考回答：**

我使用“结构化历史摘要 + 最近消息窗口 + 单条长消息压缩”。当前最近窗口保留 12 条；历史消息达到 16 条后，用消息 ID 游标定位尚未摘要的旧消息，增量更新摘要，保留风险事实、用户决策、已完成检查和待办事项，再保存摘要和游标，避免每次重处理所有历史。

超过 6000 字符的单条消息分段压缩，目标摘要不超过 2000 字符，原始内容仍留在数据库，成功的压缩结果也会保存复用。特别长的消息最多处理 8 段，只读取首尾部分时明确标记中间未检查；压缩失败则提供有限的首尾片段。

**实现边界：** 历史摘要更新失败时继续使用已有合法摘要和最近窗口，不保证保留全部历史细节。摘要作为资料单独传入，不写进系统消息；旧防护版本的摘要与压缩内容会重建。摘要本身可能遗漏内容，也会增加模型调用和 Token 消耗。

**对应代码：** `ConversationMemoryService`、`AgentMessage`、`AgentSession`。

## 12. 为什么采用 BM25 + kNN 混合检索？RRF 怎样融合结果？

**参考回答：**

BM25 适合服务名、接口名和规则编号等关键词匹配；向量 kNN 更适合理解语义相近但表达不同的问题。两路召回可以互补，但原始分数不能直接比较，所以使用 RRF 按排名融合：同一文档片段每进入一路结果，就增加 `1 / (60 + 排名)`，再按总分排序。

当前每路召回 `topK × 2` 个候选，融合后在应用层计算余弦相似度，过滤低于阈值的片段并保留 topK。检索支持文档类型和服务名过滤；`searchKnowledge` 返回原文片段、文档名称和片段编号，让模型结合规范解释 PR 风险。

**实现边界：** 当前 BM25 召回的结果也要通过余弦相似度阈值，精确关键词命中仍可能被过滤。阈值和 topK 的效果需要用评审样例验证，不能仅凭采用混合检索就声称准确率提高了某个百分比。

**对应代码：** `HybridSearchService`、`VectorIndexService`、`AgentToolsConfiguration.knowledgeSearchTool()`。

## 13. SSE 怎样把执行事件发给前端？断线如何恢复？是不是逐 Token 输出？

**参考回答：**

提交接口返回 runId 后，前端用 EventSource 单独连接该 Run 的事件接口。后端发布事件时先分配递增序号并保存到数据库，再写入 Reactor Sink；Controller 返回的 Flux 订阅事件，Spring 把事件写入 SSE 连接，前端按 `toolCall`、`toolResult`、`confirmation`、`runCompleted` 等事件类型更新页面。

事件序号作为 SSE 的 id，重连时后端根据 `Last-Event-ID` 补发之后的持久化事件，然后继续订阅实时事件。这样任务执行不依赖浏览器连接一直存在。

**实现边界：** 当前 Agent 使用非流式 ChatModel，前端实时看到的是后端执行事件；最终回答生成完后，才通过名为 `token` 的事件一次发送整段文本。实时 Sink 是进程内对象，目前没有跨实例事件广播，因此多实例下的实时推送还需要补充路由或广播机制。

**对应代码：** `AgentEventService`、`AgentController`、`AgentRunner.completeRun()`、前端 `app.js`。

## 14. DeepSeek 的 API Key、并发、Token 和调用成本怎样管理？目前有哪些不足？

**参考回答：**

项目提供 `CHAT_API_KEY` 环境配置入口，生产环境应通过环境变量或密钥服务注入真实密钥。`ChatModelManager` 根据 provider 选择厂商策略，再用 model 等配置创建客户端，方便替换模型。

Agent 通过 RabbitMQ 消费者并发、推理轮数、工具次数、上下文压缩和输出 Token 上限约束资源消耗。当前消费者每个实例为 2～4 个，模型默认输出上限为 2048 Token；这些约束有助于控制调用量，但不等于账号级并发限制或完整成本预算。

**实现边界：** 普通 `ChatService` 已接入单实例 QPS 5 的限流和 Redis 每日 50 万 Token 预算，响应完成后累计用量；Agent 与记忆摘要调用尚未接入该限流预算。Run 目前只保存最后一次模型响应的输入、输出 Token，未累计所有推理与摘要调用。现有预算先检查、后计数，并发下可能超额，也没有完整的金额核算。进一步应统一模型调用入口，控制并发，累计各轮、摘要及 embedding 用量，并按模型价格核算费用。

**对应代码：** `ChatModelManager`、`ChatService`、`RateLimitService`、`AgentRunConsumer`、`AgentRunner`。
