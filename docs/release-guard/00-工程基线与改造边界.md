# Phase 0：工程基线与改造边界

## 为什么先做基线

Agent 改造会同时触及模型、数据库、消息队列、Redis 和 SSE。如果直接修改主流程，出现问题后很难判断是原有 RAG 还是 Agent 新链路导致。因此第一阶段只处理工程基线，不改变原有问答行为。

## 本阶段实现

- `.env` 加入 Git 忽略规则，提供不含真实密钥的 `.env.example`。
- 引入 Flyway，后续表结构通过版本化 SQL 管理，不再依赖 Hibernate 自动改表。
- JPA 切换为 `ddl-auto: validate`，启动时检查实体与数据库结构是否一致。
- 引入 Spring Boot Actuator，暴露健康状态和指标端点。
- 增加 Agent 最大步骤、工具调用次数、总超时和记忆窗口配置。
- 为文档解析与 Agent 执行拆分 RabbitMQ 队列名称。

## 关键取舍

项目暂时保留 `com.interview.rag` 包名。包名重命名不会增加工程能力，却会制造大量无意义 diff；新增能力集中放到 `com.interview.rag.agent`，等核心链路稳定后再决定是否整体重命名。

外部 DevOps 系统先使用 Mock Gateway。面试时明确说明演示环境和生产适配器的边界，比伪造真实 GitLab/Jenkins 接入更可信。

## 验收

- Maven 编译通过。
- Flyway 可以在空库创建完整表结构，也可以通过 `baseline-version: 0` 接管已有数据库。
- 原有文档入库和 RAG 问答接口保持兼容。

## 面试话术

> 我没有直接把 Tool Calling 塞进原来的 ChatService，而是先固定原有 RAG 基线，引入数据库版本管理和运行指标，再逐步拆出 Agent 领域。这样每一阶段都可验证、可回退，避免一次性重写导致问题无法定位。
